{
  "title": "把推理模型的等待时间降下来",
  "summary": "从 R1 蒸馏到双偏好 DPO：短一点，也要答得好一点。"
}

DeepSeek-R1 在我们的商品问答集上得分 86，线上模型是 75。但直播间不能为了一个回复等十几秒。问题很直接：能不能留下推理能力，把计算量和输出长度降下来？

我们先做蒸馏，再压缩推理路径。前者解决模型太大，后者解决模型想得太长。

## 蒸馏：选对起点比加上 CoT 更重要

先用 5800 条商品问答数据，按 9:1 划分训练和验证集，比较三种方案：

| 学生基座与训练方式 | 回复质量分 |
| --- | ---: |
| Qwen2.5-14B，只学习最终答案 | 78 |
| Qwen2.5-14B，学习完整思考与答案 | 78 |
| DeepSeek-R1-Distill-Qwen-14B，学习完整输出 | 83 |

仅给 Qwen 加上教师 CoT，没有带来明显提升。以 R1-Distill-Qwen 为起点更有效，但 7B 版本能力不够，最终选择 14B。

量化能缓解计算压力，却解决不了长输出。扩展至 30k 条互动数据后，int8 模型平均仍需 5.58 秒，最长约 11.87 秒。这对于实时弹幕依然太慢。

## 只教短答案，还不够

最简单的方法是丢掉超过 400 tokens 的教师样本，再做 SFT。平均长度降了，但模型推理时仍可能生成很长的内容。

随后我们复现 Kimi 的 long2short DPO：对同一问题多次采样，把最短结果作为正例、最长结果作为负例。长度进一步下降，质量却从 84.9 降到 83.9。

这个偏好只告诉模型“越短越好”，没有保证短答案本身值得学。

## 同时看长度和质量

DP-DPO 的改动在样本对构造：先用 R1 评价每条采样结果，再将长度和质量归一化，计算加权分数。

<!-- image:llm-distillation-and-reasoning-compression:images/figure-bb4538013d59.png | 先领域蒸馏，再按长度与质量构造 DPO 样本对。 -->

<!-- image:llm-distillation-and-reasoning-compression:images/figure-bdaec00ef893.jpeg | 长度与质量的加权分数。 -->

其中，长度项偏好短输出，质量项偏好高分回复。每组选择最高分为正例、最低分为负例；两者差距太小就丢弃。这样可以避免把质量更差的短轨迹硬标成好答案。

权重与丢弃比例需要一起调。丢得太多，样本对看起来更清晰，训练数据却不足，泛化会变差。最终选出的正例平均比负例短 204 tokens，质量高 2.57 分。

## 压缩的效果

| 方法 | 商品问答得分 | 平均长度 | 平均耗时 | 最长耗时 |
| --- | ---: | ---: | ---: | ---: |
| 蒸馏基线 | 84.0 | 349.0 | 5.58s | 11.87s |
| 过滤长样本后 SFT | 84.9 | 308.1 | 4.93s | 9.07s |
| long2short DPO | 83.9 | 265.1 | 4.24s | 6.24s |
| DP-DPO | 85.3 | 266.0 | 4.26s | 6.53s |

这些耗时按单卡 H20、62.5 tokens/s 换算，主要反映解码成本，不是整条线上服务的实测延迟。

双偏好没有把输出压得更短，而是在接近相同长度下保住了质量。

## 验证集好，不代表线上也好

上线后，用新流量重测，3k 数据训练的 DP-DPO 从验证集的 85.3 降到 82.5，甚至低于 SFT 的线上分数 83.0。

我们把偏好数据扩到 15k，结果明显改善：

| 方法 | 验证集 | 新线上流量 |
| --- | ---: | ---: |
| DeepSeek-R1 | 85.5 | 86.0 |
| SFT | 84.9 | 83.0 |
| DP-DPO，3k 数据 | 85.3 | 82.5 |
| DP-DPO，15k 数据 | 87.3 | 84.8 |

扩充的仍是原训练期数据，不包含新流量测试集。只拿这些偏好对的正例做 SFT，也达不到 DPO 的效果，说明收益不只是筛出了更好的数据。

这次实践最值得记住的不是某个权重，而是两件事：**短输出要和质量一起优化；偏好对齐的收益要拿新流量验证。**

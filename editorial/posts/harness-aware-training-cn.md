我们把直播 Agent 的规则、工具和提示词拆到了 Harness 里，希望业务改动不必每次都重新训练模型。但很快遇到另一个问题：运行环境改了，小模型未必跟得上。

大模型通常能读懂新配置，延迟却太高；小模型够快，但在固定配置上微调后，容易记住工具名、Skill 名称和提示词的写法。

Harness-Aware Training（HAT）要解决的，就是这种“上线后环境一直变，训练时却只见过一个版本”的错位。

## 什么放在 Harness 里

我们的运行环境主要分四部分：

| 模块 | 作用 |
| --- | --- |
| Skills | 按需加载回复策略与业务规则 |
| Tools | 查询商品、库存等外部信息 |
| Prompt Pipeline | 组装当前请求需要的上下文 |
| Hooks | 检查输入、工具参数、回复与终止条件 |

调整这些配置，可以改进业务行为而不更新模型权重。实际迭代仍然需要人参与：先分析失败，再确认修改、回归评测，最后决定是否上线。

规则也不是越多越好。开发集上，第二轮 Harness 迭代同时改善了准确性和有效性，后续继续补长尾规则反而出现回退。我们因此把回归检查和停止条件放进了迭代流程。

## 训练时就让环境变化

HAT 的关键是 Harness-State Augmentation（HSA）：在任务语义不变的前提下，改变 Skill 标识、内容表达、工具 Schema、提示词结构和 Hook 配置。

不是随意破坏环境，而是让模型学会读当前规则，减少对某一套表面形式的依赖。

<!-- figure:harness-aware-training:S3.F4 | HSA 贯穿监督微调与强化学习，通用蒸馏用于恢复基础能力。 -->

训练分三步：

1. **HSA-SFT**：强教师在多样化配置中生成轨迹，过滤后训练小模型。
2. **General OPD**：在通用数据上做 On-Policy Distillation，恢复领域微调损失的通用能力。
3. **HSA-RL**：让模型在变化的模拟环境里自己调用工具、处理失败，再根据结果优化。

三个阶段各有职责：先学会任务，再补回通用能力，最后练习与变化环境交互。

## 看任务效果，也看改配置后的表现

基于 Qwen3.6-35B-A3B 的结果如下：

| 指标 | 基座模型 | HAT |
| --- | ---: | ---: |
| Live-Stream QA | 80.3 | 94.8 |
| Harness-Variant QA | 75.4 | 94.6 |

HAT 的 IFEval Prompt 得分保持在 83.5。相比之下，固定 Harness 的 SFT 会使该指标较基座下降 7.7pt。对我们来说，只提高业务集分数还不够，模型不能因此更难遵循新指令。

评测还要区分角色：用于生成训练数据的教师、RL 奖励 Judge、最终评测 Judge 与人工校准，不应混成一个信号。报告中也单独检查了这些关系。

## 部署时，别把 MTP 当成现成开关

任务训练后的主模型，不能直接接一个未适配的 MTP 头就期待加速。我们在领域数据上训练草稿头，提高投机解码接受率，再测完整 Agent 链路。

单卡 H20、开启 MTP 的部署测试中，端到端延迟为 P50 3.407 秒、P95 8.114 秒。加速在低并发下更明显，不能直接推广到所有负载。

HAT 的价值不是让模型应对任意未知变化，而是把业务中真实发生的配置变化纳入训练和评测。**既然 Harness 会迭代，就应该把这种变化当成训练条件，而不是上线后的意外。**

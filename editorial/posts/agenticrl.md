早期数字人互动是一条“意图识别—检索—生成”工作流。它能处理常见问题，但每增加一种能力，都要补标签、改分支、重新训练。一次意图判断错了，后面也很难纠正。

我们后来做了两步改造：先让模型按需调用工具，再把工具调用与回复生成拆开训练。


## 从工作流到 Agent

### 我们要接住怎样的互动

<!-- image:agenticrl:images/figure-fba13ebfdc1f.png | 数字人对弹幕进行文本与口播回复。 -->

- 观众在数字人直播间发送弹幕时，数字人主播会基于直播间商品信息、商家预设问答对等信息对观众进行弹幕和口播的回复；
- 我们的算法在这个场景下控制数字人主播对观众的互动行为，包括要回复什么、要不要调整讲品顺序到观众想听的商品等。

### 固定流程卡在哪里

面对快速变化的直播业务，原有“意图识别—检索—生成”的静态 Workflow 架构已遭遇严重瓶颈，主要体现在三大维度：

- 系统灵活性差，迭代受限：依赖人工标注，新增1个意图需2个月时间进行迭代，预置 FAQ 利用率不足2%，难以适应业务的快速迭代。
- 上下文感知弱，易死胡同：无法联动“宝贝口袋/讲解文案/历史弹幕”等多源信息，一旦意图误判无法反思回退，只能机械抛给人工客服。
- 并发调度缺失，能力遇颈：无法处理直播间高频的多弹幕并发，扩展更高阶的动作/语气交互极其困难。

让我们开始认真考虑换架构的，还有模型能力和推理成本的变化。当时，30B MoE 模型在单卡 H20 上已经能跑到 140 tokens/s，基座的工具使用能力也更可用了。原来需要写成分支的动作，开始有机会交给模型按上下文决定：缺什么信息就查什么，查错了还能回头。这给了我们一个可行的起点，但能做出演示和能稳定上线之间，仍然隔着延迟、事实质量和训练方式几个问题。

### 先让模型决定下一步

完成了从 Workflow 架构到 Agentic 架构的升级：

- 感知域：单维度匹配  →  全局上下文感知（弹幕+历史+商品信息融合）
- 决策域：单次死板分类  →  多次按需工具调用与自我纠错（反思机制）
- 执行域：单意图话术  →  多模态响应（调图、调顺序、融合讲解文案）

- 为了让大家更好的了解我们的agent的执行流程，这里给出一个，Agent 完整 trajectory 的示例：

```text
观众问题：索尼 XM4 和 XM5 哪个降噪好？
上下文：主播正在讲解另一款商品。
1. 分别检索 XM4、XM5 的商品信息。
2. 根据工具结果判断是否足以比较。
3. 加载对应回复规则，再生成最终回复。
```

### 再把延迟和回复质量拉回可用范围

直播互动要求低延迟，同时还要保证回复正确、有帮助。模型优化分别从这两方面入手：

- 延迟：用大教师生成完整轨迹，再将工具调用与回复分别蒸馏到 30B-A3B 学生。单次工具调用生成约 0.3s，单 H20 解码吞吐为 140 tokens/s。这是工具调用生成的耗时，不包含一次完整互动的其余环节。
- 回复质量：在互动数据上定义正确性与帮助性奖励，让回复模型依据工具返回的信息作答。商品事实、无依据承诺都要检查，模型需要分清哪些可以说，哪些要保留或继续询问。

- AgentTuning蒸馏

多一次查资料、反思或修正，就多一轮推理时间。我们先采样大教师的交互轨迹，再通过 AgentTuning 把规划、工具选择和回复行为教给小模型，使这些能力能在直播间的时延预算内运行。大教师用于生成训练轨迹，不处理上线后的每条请求。

<!-- image:agenticrl:images/figure-9a1f6e0128ef.png | 将教师轨迹中的工具调用与最终回复分别蒸馏。 -->

- 教师模型在 Agent 推理过程中与环境进行多轮交互，采样出完整的 agent 执行 trajectory，其中，我们将大模型的工具调用及回复能力分别蒸馏至两个 Qwen3-30B-A3B 的小模型中；
- 为了追求低延迟，学生模型均采用 Instruct 模型，在蒸馏时剔除掉了教师模型的思考部分序列：

- 工具调用模型仅蒸馏教师 Agent 的工具调用生成部分，截取最后一轮工具调用前的 trajectory，并 mask 掉工具调用结果；
- 回复生成模型仅蒸馏教师 Agent 最终回复生成部分，mask 掉回复前的所有序列。

- 回复模型 RLVR

蒸馏后，学生能规划和调用工具，但最终回复仍可能误读材料，或做出证据之外的承诺。我们从 AgentTuning checkpoint 继续对回复模型做 GRPO：在相同工具链前缀下采样多条回答，用正确性、帮助性和长度奖励比较。正确性约束事实，帮助性防止过度保守，长度限制多余展开，优化只针对最终回复。

<!-- image:agenticrl:images/figure-827d2e0e6f54.jpeg | 固定工具链前缀，仅优化最终回复的 RLVR。 -->

- 输入数据为教师模型预先打标好的工具调用链，对于一条前缀工具调用链模型 rollout 出多条回复组成一组；
- 对于每个回复进行事实正确性和帮助性的打分，并在组内计算均值与标准差算出组内优势，根据优势计算出 loss 对模型进行优化；
- 整体目标：

- 回复模型尽可能减少幻觉，按照工具调用结果进行回复；
- 为避免模型为了降低幻觉变得过于保守，增加帮助性鼓励模型更多的满足观众实际需求；

在 ROLL 里，我们保留教师轨迹的 `messages[:-1]` 作为前缀，让 rollout 只生成最后一条回复。`tokenizer.apply_chat_template` 整理输入格式，RLVR 只更新生成的回复。前缀提供条件，回复参与训练，两部分的 token 要分开处理，才能把奖励和 loss 放到正确位置。

## 让学生自己进环境练习
### 蒸馏之后，还缺什么

上线版工具模型通过教师轨迹蒸馏得到，能学到的行为受样本覆盖限制。接下来，我们尝试让学生自己在环境中调用工具，从选择、反馈和修正中学习。对于教师没有演示过的路径，学生可以在训练中探索，不必完全依赖补充标注轨迹，这就是后面的 Agentic RL 实验。

### 先尝试完整交互的 RL

<!-- image:agenticrl:images/figure-df52e743cd22.jpeg | Rollout、环境执行和奖励计算的工程链路。 -->

Rollout 阶段：

1. Policy 模型在模拟环境中进行多轮工具调用交互，最终以获取回复规则并产生非工具调用回复为结束标志；
2. 针对每个 rollout 计算工具调用与最终回复奖励，并计算组内优势；

训练阶段：

1. 仅针对包含工具调用和最终回复的模型生成部分序列计算 loss，其余包含输入数据、工具返回序列均 mask 掉；
2. 采用初始化 reference model 计算 KL 散度，重要性采样部分与基础 GRPO/PPO 设置无异；
3. 参数由训练模型更新至推理模型继续下一轮 Agentic RL 训练，Agent 模型在训练过程中同时优化工具调用与回复能力。

### 训练集群和沙盒怎么配合

ROLL 中的 Agentic RL 仿真分成训练侧和远程沙盒两部分：

- 训练侧：rollout 线程驱动模型产生完整轨迹，调用奖励模型评分，再整理参与训练的 token。序列、mask 和分数交给训练阶段，完整过程会保留，其中策略输出需要单独标记。
- 远程沙盒：负责内部 RPC 等受限接口、有状态容器和即时模拟器。训练线程通过沙盒服务与环境交互，各轮状态和工具返回由这一侧单独管理。

整体训练与交互流程包含以下四个关键步骤：

- 初始化环境。每个 rollout 线程对应一个仿真实例，向平台服务建立直播间状态，拉取基础信息、构建语义向量库并初始化远程工具链。模型和环境需要从相同的任务状态开始。

- 执行交互。线程调用进程内的 vLLM 或 SGLang，解析工具请求后访问远程沙盒，将返回结果交给模型继续生成。达到轮数上限或调用“获取最终回复”等终止工具后，一次 rollout 结束，记录保留整个过程。

- 评分和整理序列。通过内部接口调用 LLM Judge，给交互轨迹打 episode reward；token mask 排除系统提示、输入和工具返回，只让模型自己生成的决策参与 loss。环境返回的内容作为条件，不是策略要学习生成的内容。

- 更新参数。自定义实现返回 token 序列、mask 和轨迹分数，ROLL 计算 advantage 与 loss，再通过 Megatron 更新模型。参数同步到 vLLM 或 SGLang 后，才进入下一轮 rollout。排查训练时也要确认同步是否完成，避免分数已经变化、推理却仍使用旧参数。

ROLL 封装了大部分训练流程，我们主要接入 rollout、token mask 和 reward。Chat template 的 mask 未必符合任务所需，需要按轨迹结构核对，尤其是工具返回和系统消息。它们虽然也使用 message 格式，但不属于模型生成的动作。

早期训练中，仿真不稳定和 reward 无法区分轨迹好坏，是两个主要问题。仿真不稳定会让同一策略的反馈失去可比性；reward 区分不清，模型就得不到有效的更新方向。要判断训练曲线是否可靠，先得解决这两项。

### 为什么只给最终奖励还不够

初期端到端 Agentic RL 没有训出效果足够好的模型，主要有以下问题：

- 最终的正确性、帮助性奖励更多的是偏向回复模型而设计的，而模型的 Agentic 能力并没有在其中得到清晰反馈而良好的训练，反而因为不恰当的奖励而变得更差；
- 直接在最终奖励中加上基于 llm judge 的工具调用奖励后，虽然能带来对于工具调用的反馈，但由于 llm judge 不稳定的特点，奖励也变得更加模糊，强化学习训练变得更加难以收敛；
- 工具调用需要理解弹幕与上下文、选择接口和参数，再根据返回结果决定是否继续查。回复则要保证事实、满足观众需求，并且表达自然。把最终回复分数分配给前面每次调用，难以区分这些职责。

## 把工具调用和回复分开训练
- 我们将系统拆为工具调用 Agent 和回复 Agent，分别设计奖励，同时保留环境中的协作。工具 Agent 获取信息，回复 Agent 使用信息，两者在联合训练中都能看到对方行为变化后的结果。

### 两个 Agent，怎么一起更新

- 目前我们的互动 Multi-Agent RL 实现如下，人为的分为了工具调用模型以及回复（总结）模型，在训练中，工具调用模型仅优化工具调用部分，回复模型仅优化回复部分：

<!-- image:agenticrl:images/figure-d8f26ee8a122.png | 工具 Agent 与回复 Agent 共享环境、分别接收奖励。 -->

- 工具调用模型在模拟的直播互动环境中进行多轮交互，得到 K 条 Agent 工具调用路径，工具调用阶段以获取回复规则作为结束标识，如果工具调用阶段未获取回复规则则不会产生回复；

<!-- image:agenticrl:images/figure-7eced5389703.png | 不同 Agent 的奖励分工。 -->

Rollout阶段：

1. 工具调用模型和环境服务（内部仿真环境平台）进行多轮交互，在环境判断是否工具调用结束进行回复（以超过调用轮次限制以及调用 `获取回复规则`工具作为终止符号）；
2. 工具调用模型调用结束后，回复模型以工具调用链作为前缀，按照回复规则生成回复；
3. 基于完整 trajectory 分别为工具调用阶段与回复阶段计算 reward；
4. 并基于计算好的 reward 分别为工具调用模型与回复模型赋值组合加权 reward 并计算组内优势。

训练阶段：

1. 对于工具调用模型：截取最终回复前最后一轮工具调用的 trajectoy，mask 掉其中工具调用返回结果部分，采用对应计算出的工具优势计算 loss；
2. 对于回复模型：取完整 trajectory，mask 掉非最终回复前置部分，采用对应计算出的回复优势计算 loss；
3. 对于这两个模型都采用各自的初始化 reference model 计算 KL 散度，重要性采样部分与基础 GRPO/PPO 设置无异。
4. 针对两个模型分别将参数由训练模型（megatron）更新至推理模型（vllm），并继续下一轮训练。

这组任务拆成两个 Agent 后，比端到端单 Agent RL 更容易收敛。长交互被分为更接近 RLVR 的子任务，各模型得到的反馈更直接，错误也更好定位。这个结果依赖环境、mask 和奖励的正确实现，拆分模型本身并不保证同样的收益。

Multi-Agent RL 的数据组织与 step reward 接近。暂不考虑不同 Agent 的参数归属时，可以参考这套流程搭建训练，ROLL 中的 GiGPO 等实现也可复用。接入双模型后，还需要核对序列、奖励和 checkpoint 分别属于哪个 Agent。

双模型的 checkpoint 要自动保存并区分归属。我们用 `cluster_name` 在 `ckpt_id` 维度标识模型，复用 ROLL 到 OPENLM MOS 的自动上传流程。这样能保存同一轮协同训练的两侧结果，后续也可以成对加载、回放。

### 训练曲线里要看什么

<!-- image:agenticrl:images/figure-266baeef002c.png | 回复质量与工具合理性的实验结果。 -->

- 图中使用相同的奖励对于单 Agent Agentic RL 和多 Agent Agentic RL 进行了训练实验，均使用 GRPO 作为模型优化算法：

- 单 Agent 对4个奖励进行加权求和的方式计算组合 reward；
- 多 Agent 的回复模型采用正确性和帮助性的加权求和，工具调用模型采用规则遵守和工具调用的加权求和；

- 单 Agent 将多种奖励相加后，这组实验难以稳定改善。拆成工具与回复两个 Agent，反馈更接近各自的任务，训练变化也更好解释。差别主要在两处：

- 正确性和帮助性主要在评最终回复。只根据最终有没有幻觉，就给前面的每次工具调用分配好坏，反馈会比较间接，甚至可能鼓励错误的路径。
- 反过来也一样：工具调用合理性关注信息获取过程，用它直接评价最终回复，仍然会漏掉事实表达和用户需求这两部分。

### 与监督微调版本比一比

<!-- image:agenticrl:images/figure-bb193e83747b.png | 多智能体协同训练的消融对比。 -->

- 本实验与前述架构升级实验为分别设计的独立实验，主要改动来自于对事实正确性、回复帮助性 LLM Judge 的迭代升级以及蒸馏教师模型采用了更加强大的 GLM 4.7 模型；
- 为了解决此前系统仅关注最终回复效果而导致工具调用能力在优化后下降的缺陷，我们单独将工具调用合理性这一 LLM Judge 指标作为测试集指标以监控模型的工具调用能力。

- 相对这组实验的 SFT 基线，回复正确性提高 4.1pt、帮助性提高 23.6pt，工具调用合理性提高 18.2pt。两部分分别记录，再检查完整系统，避免最终回复分数掩盖工具能力的变化。

### 收益来自哪里

<!-- image:agenticrl:images/figure-087efade9246.png | 不同训练与奖励配置的对比。 -->

- 另一组对照固定工具模型，只对最终回复做 RLVR，用来区分收益是否仅来自回复更符合奖励偏好，以及上游信息获取是否也有贡献。
- 在实验中，Multi-Agent RL 方法相较于固定工具调用模型仅 rlvr 训练回复模型的方法在事实正确性上提升5.6pt，在帮助性上提升6.6pt，而工具调用合理性保持了对 SFT 模型的优势（+18.2pt）。

总结与未来展望

- 总结：

- 第一阶段改造了架构：模型结合上下文选工具，替代固定意图分支。随后用蒸馏将多轮决策迁移到较小的 MoE 模型，用 RLVR 优化回复，以满足直播延迟预算。工具调用生成达到亚秒级，完整互动耗时仍按前面的端到端结果统计。线上 A/B 反映的是整套链路的变化，不能归到单个模型。
- 第二阶段转向训练：搭建仿真，让 Agent 自己完成多轮交互，再检查最终回复奖励能否指导前面的决策。我们增加工具调用合理性评估，将工具和回复拆为两个协同训练的 Agent。这有助于定位收益和错误，判断问题需要改奖励，还是需要回到环境中处理。

- 当前互动算法局限与未来展望：

- Workflow 升级为 Agent 后，基础链路已经跑通。后续要继续增加数字人专属工具，设计更复杂的交互，利用 Agentic 架构与 LLM 的能力。
- 当前 Multi-Agent 基本是来自于单 Agent ReAct 架构的阶段性解耦策略，更接近于 Dr.MAS 这样的串行 Multi-Agent，类似于 sub-agent、agent-swarm 等并行化 Multi-Agent 优势仍未体现出来；
- 目前训练仍围绕具体任务。新增工具或信息时，旧模型未必能直接使用，既需要改善泛化，也可以通过 Skill 的渐进式披露在运行时提供用法。后续 Harness 工作继续处理模型如何适应环境变化的问题。

## 怎么理解这些结果

线上 A/B 与离线 Multi-Agent RL 是不同阶段的实验。1.79 秒的平均端到端延迟、下降 1.36 秒，以及多轮用户比例提升 2.76%，对应的是从 Workflow 升级到 Agentic 架构后的线上对比；不能直接归因于后面的 Multi-Agent RL。

正确性 +4.1pt、帮助性 +23.6pt、工具合理性 +18.2pt，是离线训练相对监督微调模型的变化。各实验的教师与 Judge 配置不同，应分别核对基线、输入和判分口径，这几组表格不构成一次统一的因果实验。

落地时需要保留完整轨迹，才能追查缺少了什么信息、为什么调用某个工具，以及奖励是否鼓励了预期行为。拆成两个 Agent 后，这些问题更容易定位和优化。

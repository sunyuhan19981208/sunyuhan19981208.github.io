We moved business rules, tools, and prompts into a Harness so that every operational change would not require retraining. Then we met a second problem: the compact model did not always follow the updated runtime.

Large models could often interpret new configurations, but were too slow. Small models were fast, yet fixed-configuration fine-tuning encouraged them to memorize tool names, Skill identifiers, and prompt wording.

Harness-Aware Training (HAT) addresses that mismatch: the environment keeps changing after deployment, while training usually exposes the model to one version.


## The runtime has to change faster than the model

<p>A digital-avatar host answers product questions, handles casual conversation, and invokes tools during a live stream. Unlike a private chat assistant, it may speak to the entire room. A wrong price, unsupported product claim, or invented promise can therefore affect many viewers at once. Each request must combine the viewer message with product information, live-room state, and dialogue history, then produce a useful reply within a tight latency budget.</p>

<p class="ltx_p" id="S2.SS2.p1.1"><span class="ltx_text" id="S2.SS2.p1.1.1">The Harness Agent runtime comprises four mechanisms. </span><em class="ltx_emph ltx_font_italic" id="S2.SS2.p1.1.2">Skills</em><span class="ltx_text" id="S2.SS2.p1.1.3"> are dynamically loaded behavioral modules for Q&amp;A strategy, tool choosing, and reply style. The </span><em class="ltx_emph ltx_font_italic" id="S2.SS2.p1.1.4">System Prompt Pipeline</em><span class="ltx_text" id="S2.SS2.p1.1.5"> assembles instructions from product specifications, retrieved FAQ, living-room status, global boundary and active skill descriptions. </span><em class="ltx_emph ltx_font_italic" id="S2.SS2.p1.1.6">Hooks</em><span class="ltx_text" id="S2.SS2.p1.1.7"> validate inputs, parameters, and output formats, triggering correction or retry when needed. </span><em class="ltx_emph ltx_font_italic" id="S2.SS2.p1.1.8">Tool Registry</em><span class="ltx_text" id="S2.SS2.p1.1.9"> connects the agent to external product, inventory, and commerce services. Because these modules are versioned independently of model weights, a new skill or tool can be deployed as a harness change rather than a retraining cycle. The overview of our harness agent architecture is shown in Fig. </span><a class="ltx_ref" href="https://arxiv.org/html/2608.15763v5#S2.F1"><span class="ltx_text ltx_ref_tag">1</span></a><span class="ltx_text" id="S2.SS2.p1.1.10"> (b).</span></p>

<p class="ltx_p" id="S2.SS4.SSSx1.p1.1"><span class="ltx_text" id="S2.SS4.SSSx1.p1.1.1">In single-comment mode, the runtime handles one viewer message independently. In multi-comments mode, it aggregates related messages before responding. An available internal traffic summary groups the main viewer intents as shown in Table </span><a class="ltx_ref" href="https://arxiv.org/html/2608.15763v5#S2.T1.fig1"><span class="ltx_text ltx_ref_tag">1</span></a><span class="ltx_text" id="S2.SS4.SSSx1.p1.1.2">.</span></p>

<p class="ltx_p" id="S2.SS4.SSSx2.p1.1"><span class="ltx_text" id="S2.SS4.SSSx2.p1.1.1">The Harness exposes built-in interfaces for retrieval, commerce operations, and flow control. Additional marketing interfaces are discovered dynamically from an external service through the Model Context Protocol (MCP). Table </span><a class="ltx_ref" href="https://arxiv.org/html/2608.15763v5#A1.T11"><span class="ltx_text ltx_ref_tag">11</span></a><span class="ltx_text" id="S2.SS4.SSSx2.p1.1.2"> groups the release inventory by responsibility.</span></p>

<p class="ltx_p" id="S2.SS4.SSSx3.p1.1"><span class="ltx_text" id="S2.SS4.SSSx3.p1.1.1">Each Skill is a versioned Markdown module with YAML metadata and behavioral directives. The runtime requires at least one Reply Skill before a substantive final response. Strategy Skills are optional and can be composed when an interaction requires a specialized tool chain. Table </span><a class="ltx_ref" href="https://arxiv.org/html/2608.15763v5#A1.T12"><span class="ltx_text ltx_ref_tag">12</span></a><span class="ltx_text" id="S2.SS4.SSSx3.p1.1.2"> records the release inventory. Module names and versions are reconciled against the same manifest before promotion.</span></p>

A request is normalized into product, FAQ, room, and dialogue context. The prompt pipeline assembles the active instructions; a bounded agent loop loads Skills and invokes tools; Hooks check parameters, required Skills, format, and factual risks. The runtime then strips internal reasoning from the spoken reply while retaining the structured trajectory for inspection.

## Evolve the Harness while keeping the policy fixed

<p class="ltx_p" id="S2.SS3.p1.1"><span class="ltx_text" id="S2.SS3.p1.1.1">We introduce </span><em class="ltx_emph ltx_font_italic" id="S2.SS3.p1.1.2">Harness Evolution</em><span class="ltx_text" id="S2.SS3.p1.1.3"> to denote a controlled process that improves the agent by changing skills, prompts, hooks, or tools while holding the model fixed. It is human-in-loop rather than fully autonomous: AI performs failure clustering, diagnosis, and proposed edits, a developer confirms the plan, runs evaluation, and decides whether to promote, revise, or stop. The complete operational protocol appears in Appendix </span><a class="ltx_ref" href="https://arxiv.org/html/2608.15763v5#A2"><span class="ltx_text ltx_ref_tag">B</span></a><span class="ltx_text" id="S2.SS3.p1.1.4">.</span></p>

<p class="ltx_p" id="S2.SS3.p3.1"><span class="ltx_text" id="S2.SS3.p3.1.1">Figure </span><a class="ltx_ref" href="https://arxiv.org/html/2608.15763v5#S2.F2"><span class="ltx_text ltx_ref_tag">2</span></a><span class="ltx_text" id="S2.SS3.p3.1.2"> illustrates both the value of the </span><em class="ltx_emph ltx_font_italic" id="S2.SS3.p3.1.3">Harness Evolution</em><span class="ltx_text" id="S2.SS3.p3.1.4">. On the dev-set annotated by three annotators. Evolution 1 sharply improves Accuracy from 82.40 to 92.13 but reduces Effectiveness to 84.16. Evolution 2 reaches 92.55 Accuracy and 92.75 Effectiveness. Additional long-tail rules in Evolutions 3–4 regress one or both dimensions, so Evolution 2 is selected as the engineering early-stop checkpoint. Detailed module changes, category diagnostics, stopping logic, and evidence boundaries are reported in Appendix </span><a class="ltx_ref" href="https://arxiv.org/html/2608.15763v5#A2"><span class="ltx_text ltx_ref_tag">B</span></a><span class="ltx_text" id="S2.SS3.p3.1.5">. The evaluation Judge is also implemented as an editable harness agent as detailed in Appendix </span><a class="ltx_ref" href="https://arxiv.org/html/2608.15763v5#A2.SS4"><span class="ltx_text ltx_ref_tag">B.4</span></a><span class="ltx_text" id="S2.SS3.p3.1.6">.</span></p>

The practical cycle is diagnosis, human review, an editable Harness change, evaluation, and regression checking. The model can help cluster failures and suggest edits; people decide whether the proposal is justified and whether to deploy, revise, roll back, or stop. A long tail of isolated failures is a reason to reconsider another rule, not proof that iteration must continue.

<p class="ltx_p" id="S3.SS2.p1.1"><span class="ltx_text" id="S3.SS2.p1.1.1">The method is proposed to solve </span><em class="ltx_emph ltx_font_italic" id="S3.SS2.p1.1.2">surface-form overfitting</em><span class="ltx_text" id="S3.SS2.p1.1.3">: when training data contains a single, fixed harness, the objective permits shortcuts such as matching skill names by string similarity, selecting tools from memorized schema text, or following instructions only in a familiar template. The core hypothesis is that changing the surface form of the harness makes it harder for the model to rely on fixed names or templates as shortcuts. If a skill is renamed, its description rewritten, and distractors injected, functional information about the skill becomes more useful for routing than memorizing a single identifier.</span></p>

<p class="ltx_p" id="S3.SS2.p2.1"><span class="ltx_text" id="S3.SS2.p2.1.1">We perturb the harness along five dimensions, each targeting a distinct aspect of surface-form dependence:</span></p>

<p class="ltx_p" id="S3.I1.i1.p1.1"><em class="ltx_emph ltx_font_italic" id="S3.I1.i1.p1.1.1">Skill Identifier:</em><span class="ltx_text" id="S3.I1.i1.p1.1.2"> We expand the skill set with synthetic plausible skills and noise skills, randomly mask subsets of existing skills, rename skills, and rewrite skill descriptions by a strong language model. These changes reduce the usefulness of a fixed skill identifier.</span></p>

<p class="ltx_p" id="S3.I1.i2.p1.1"><em class="ltx_emph ltx_font_italic" id="S3.I1.i2.p1.1.1">Skill Content:</em><span class="ltx_text" id="S3.I1.i2.p1.1.2"> Within each skill, we paraphrase individual rules, randomly mask a subset, and reorder them. This variation is intended to reduce reliance on rule position and exact wording.</span></p>

<p class="ltx_p" id="S3.I1.i3.p1.1"><em class="ltx_emph ltx_font_italic" id="S3.I1.i3.p1.1.1">Tool Definition:</em><span class="ltx_text" id="S3.I1.i3.p1.1.2"> We rename tools, rewrite descriptions. This transformation makes name matching less reliable while preserving the tool’s function.</span></p>

<p class="ltx_p" id="S3.I1.i4.p1.1"><em class="ltx_emph ltx_font_italic" id="S3.I1.i4.p1.1.1">System Prompt:</em><span class="ltx_text" id="S3.I1.i4.p1.1.2"> We reorder top-level instruction blocks and items within blocks, and perturb numeric constraints (e.g., response length limits, maximum interaction rounds) within operationally valid ranges.</span></p>

<p class="ltx_p" id="S3.I1.i5.p1.1"><em class="ltx_emph ltx_font_italic" id="S3.I1.i5.p1.1.1">Hook:</em><span class="ltx_text" id="S3.I1.i5.p1.1.2"> We design controlled variants of retry behavior, message structure, and hook-triggered modifications to simulate the changes that the model may encounter after hooks are updated in production.</span></p>

### HSA-SFT: demonstrations under varied Harness states

<p>Start from real live-room requests containing viewer messages, room state, and product context. HSA creates additional task-preserving Harness variants. A strong teacher generates candidate trajectories under both the original and augmented states, so supervision spans several ways of expressing the same operational rules.</p>

<p>Quality filtering checks Accuracy and Effectiveness before a trajectory reaches the student. The supervised corpus therefore teaches both how to act in the task and how to interpret the current configuration, rather than associating one tool name with one fixed behavior.</p>

<p>Hook retries need special treatment. Most demonstrations remove intermediate failures and retain the final valid behavior, avoiding a policy that routinely makes an avoidable error before fixing it. A smaller set keeps complete retry histories so the student can still understand a Hook message and recover when something does go wrong.</p>

### General OPD: recover instruction following

<p class="ltx_p" id="S3.SS4.SSS0.Px2.p1.1"><span class="ltx_text" id="S3.SS4.SSS0.Px2.p1.1.1">Motivated by prior practice showing that On-Policy Distillation can improve general instruction-following ability </span><span class="ltx_text" id="S3.SS4.SSS0.Px2.p1.1.5">, we add a General OPD stage after HSA-SFT. We use the pre-HSA-SFT base model as the teacher and perform on-policy distillation on the Tulu3 </span><span class="ltx_text" id="S3.SS4.SSS0.Px2.p1.1.9"> general instruction dataset. The student samples responses on-policy for Tulu inputs and is trained by minimizing the KL divergence between the student distribution and the base-model distribution:</span></p>

### HSA-RL: learn from the policy’s own interaction

<p>Starting from HSA-SFT plus General OPD, the policy rolls out complete interactions in the simulator. Each rollout can involve Skill selection, several tool calls, result interpretation, a retry, and the final response. This stage optimizes the student’s own behavior under changed Harness states rather than asking it to imitate another fixed collection of teacher traces.</p>

<p class="ltx_p" id="S3.SS4.SSS0.Px3.p2.1"><span class="ltx_text" id="S3.SS4.SSS0.Px3.p2.1.1">Within the simulated environment, we optimize the policy based on Group Relative Policy Optimization (GRPO) </span><span class="ltx_text" id="S3.SS4.SSS0.Px3.p2.1.5">. <p class="ltx_p" id="S3.I3.i1.p1.1"><em class="ltx_emph ltx_font_italic" id="S3.I3.i1.p1.1.1">Accuracy</em><span class="ltx_text" id="S3.I3.i1.p1.1.2">: whether the final response contains factually correct information and follows the instructions defined in prompts or skills. Applied on reply state;</span></p>

<p class="ltx_p" id="S3.I3.i2.p1.1"><em class="ltx_emph ltx_font_italic" id="S3.I3.i2.p1.1.1">Effectiveness</em><span class="ltx_text" id="S3.I3.i2.p1.1.2">: whether the response adequately addresses the user’s intent with appropriate detail and actionability. Applied on reply state;</span></p>

<p class="ltx_p" id="S3.I3.i3.p1.1"><em class="ltx_emph ltx_font_italic" id="S3.I3.i3.p1.1.1">Tool Rationality</em><span class="ltx_text" id="S3.I3.i3.p1.1.2">: whether the tool invocation chain is logically sound and efficiently structured (no redundant calls, correct parameter usage), this reward can prevent model from overfitting to specific tools. Applied on tool state;</span></p>

<p class="ltx_p" id="S3.I3.i4.p1.1"><em class="ltx_emph ltx_font_italic" id="S3.I3.i4.p1.1.1">Skill Selection</em><span class="ltx_text" id="S3.I3.i4.p1.1.2">: whether the model correctly identifies the user’s intent and the current context to load the appropriate Skills, this reward can prevent model from overfitting to specific skills. Applied on tool state.</span></p>

Tool and reply segments form separate groups for advantage computation. Tool rationality and Skill selection assess the interaction path; Accuracy and Effectiveness assess the final reply. The reported implementation combines GRPO with reward-dimension normalization and sequence-level importance sampling. An auxiliary length term discourages unnecessary reasoning without replacing the task rewards.

## The simulator is part of the method

<p>Demonstrations cover the teacher’s successful paths, but a deployed student also encounters its own mistakes: a wrong Skill, malformed arguments, a tool timeout, or a Hook requesting revision. HSA-RL lets the student experience these consequences and practice recovery instead of learning only the final successful trajectory.</p>

<p>The simulator implements the production control flow rather than returning a single static answer. Its four parts are input sampling, Harness scheduling, sandboxed tool execution, and configuration augmentation.</p>

<p>Inputs come from processed live-stream scenarios, including product inquiries, casual chat, purchase intent, after-sales questions, and messages containing several intents. Each is paired with product, dialogue, and live-room context.</p>

<p>Scheduling handles Skill routing, parameter and response checks, required Skill loading, retries, and the bounded multi-turn loop. The sequence of state transitions is retained for training and inspection.</p>

<p>Sandboxed tool executors replay product details, prices, and inventory from controlled data. Fault injection adds timeouts, malformed results, or rejected operations so recovery is represented in training.</p>

<p>The same augmented Harness state governs both the policy and its environment. Renaming an interface without updating the executor would create a broken task, not a useful robustness example.</p>

We also evaluate general instruction-following ability on the public IFEval benchmark </span><span class="ltx_text" id="S4.SS1.p1.1.7">. To test actual deployment latency and serving performance, we use a fixed complete-Agent deployment replay. <p class="ltx_p" id="S4.SS2.p1.1"><span class="ltx_text" id="S4.SS2.p1.1.1">For Live-Stream QA and Harness-Variant QA, we evaluate each response with Accuracy and Effectiveness using the Harness-based Agent-as-a-Judge, following the LLM-as-a-Judge paradigm </span><span class="ltx_text" id="S4.SS2.p1.1.5">. ## What the stage ablations show

<p>Fixed-Harness SFT improves business performance but damages general instruction following. In the reported pathway, IFEval Prompt drops by 7.7 points and synthetic prompt robustness also declines. The task can therefore look better on its original configuration while the model becomes less capable of obeying the next configuration.</p>

<p>HSA-SFT and General OPD address different parts of this problem. Variation during SFT prevents much of the surface-form dependence; OPD recovers capability that was still lost. General OPD restores 8.5 IFEval points after fixed-Harness SFT but only 0.2 after HSA-SFT, which had already preserved more of the base model’s general ability.</p>

<p>RL raises the business metrics in both branches, but a fixed training environment can again sacrifice generalization. The stronger result comes from applying HSA during RL as well as SFT. This is a stage-wise ablation, not evidence that adding any augmentation to any task will necessarily help.</p>

## Can the model follow a real Harness edit?

<p class="ltx_p" id="S5.SS6.p1.1"><span class="ltx_text" id="S5.SS6.p1.1.1">We construct an additional held-out evaluation set for Harness edits by sampling 1,500 cases from real online live-streaming traffic, with 500 development cases and 1,000 held-out test cases. The raw logs contain viewer comments, dialogue history, live-room context, product information, tool-use traces, and model responses. We use an automatic quality check to count bad cases where the model output is not sufficiently natural or colloquial for a live-streaming host.</span></p>

<p class="ltx_p" id="S5.SS6.p2.1"><span class="ltx_text" id="S5.SS6.p2.1.1">The development split is used only for Harness diagnosis and editing. We analyze the bad cases on the 500-case development set and revise editable Harness components, primarily the system prompt and Skills, while keeping the model weights fixed. The resulting Harness edits are fixed and applied unchanged to both the Fixed-Harness SFT checkpoint and the HAT checkpoint. The test split is held out from this editing loop and is used to compare each model before and after applying the same Harness edits.</span></p>

<p class="ltx_p" id="S5.SS6.p3.1"><span class="ltx_text" id="S5.SS6.p3.1.1">On the held-out test set, the Harness edits reduce the total detected error count by 18.1% for the Fixed-Harness SFT checkpoint and by 51.7% for the HAT checkpoint, relative to their respective before-edit counts. Since lower error counts are better, these results show that the same Harness edits improve both models, with a substantially larger reduction for HAT.
Figure </span><a class="ltx_ref" href="https://arxiv.org/html/2608.15763v5#A2.F8"><span class="ltx_text ltx_ref_tag">8</span></a><span class="ltx_text" id="S5.SS6.p3.1.2"> in Appendix </span><a class="ltx_ref" href="https://arxiv.org/html/2608.15763v5#A2"><span class="ltx_text ltx_ref_tag">B</span></a><span class="ltx_text" id="S5.SS6.p3.1.3"> provides two qualitative examples in which the Fixed-Harness SFT checkpoint continues to expose internal uncertainty after the shared prompt edit, whereas HAT follows the revised Harness instruction. These cases illustrate edit compliance but do not constitute additional quantitative evidence.</span></p>

The held-out split matters here: the 500 development cases guide editing, while the 1,000 test cases evaluate the edited configuration. The 51.7% versus 18.1% error reductions support adaptation within this edit protocol; they do not establish robustness to arbitrary tools or an unseen business domain.

## Production evidence and the limits of the claim

In the 100-request human blind test, 64 pairs are ties, 35 favor Harness, and one favors ReAct. The 97.2% non-tie win rate uses only the 36 decisive pairs. It is not a 97.2% win rate over all requests. The annotators inspect complete traces as well as final replies, which helps attribute gains to input understanding, evidence handling, and scenario-appropriate behavior.

The production A/B test uses UV-normalized item-page views and reports approximately 0.91% improvement over ReAct. It is an engagement measure under that traffic experiment, not a direct claim about purchase conversion. The offline, blind-test, and online comparisons answer different questions and retain different baselines.

For reproducibility, bind each result to the model checkpoint, Harness revision, tool registry, and serving configuration. HAT brings the kinds of runtime changes that actually occur in this business into training. Its value is the complete loop: express changes in the Harness, expose the model to them, then use held-out evaluation and deployment replay to decide whether the system improved.
